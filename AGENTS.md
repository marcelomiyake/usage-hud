# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, and others) working in this repository. Humans are welcome to read along.

## What this project is

usage-hud shows how much of your Claude usage you have left, at a glance, in the Claude Code status line. The line has icons and no words: `🪟 45.2k/1M  🕔 23%  📅 41%`. That is the context window's fill over its size, the 5-hour session window, and the weekly window. A `🎁 Oct 30` with the expiry date is added when a usage-limit reset is known to be available.

Claude Code is the first tool it supports, as a mod (a Claude Code plugin with a hooks module). The repository root is the plugin (`.claude-plugin/plugin.json`, `hooks/`) and also its own marketplace (`.claude-plugin/marketplace.json`, with `source: "./"`). Other tools can come later, so the usage model is kept apart from every tool's API.

## Architecture: the dependency rule

The code follows Domain-Driven Design and Clean Architecture. Dependencies point inward only:

```
src/infrastructure/<tool>/  ──▶  src/core/application/  ──▶  src/core/domain/
   (Claude Code mod)               (use case, ports)          (entities, value objects, rules)
```

- `src/core/domain/`: the model. `TokenCount`, `ContextWindow`, `UsageLimit` (the `session` and `weekly` windows), `ResetOffer`, the `UsageSnapshot` aggregate, and `StatusLine`, which turns a snapshot into the icon line. It imports nothing outside `domain/`.
- `src/core/application/`: the `ShowUsage` use case, the `UsageReading` input (plain data that `snapshotOf` validates into a snapshot), and the ports in `ports/`: `UsageSource`, `Clock`, `StatusDisplay`. It imports only from `domain/` and `application/`.
- `src/core/index.ts`: the core's public surface. Infrastructure imports from here, never from deeper files.
- `src/infrastructure/claude-code/`: the Claude Code mod. `register.ts` is the composition root and the only file that touches the engine's `$`. It answers the three ports with `$.session.usage()`, `$.clock.now()` and `$.ui.status()`. `session-usage.ts` maps Claude Code's figures to a `UsageReading` and is free of `$`.

Rules that keep it that way:

- Never import from `src/infrastructure/` inside `src/core/`, and never import `claude-code` in `src/core/`.
- `src/core/` runs inside the Claude Code mod sandbox, which has no DOM and no Node. Use only standard ECMAScript 2023 there: no `node:` modules, no `process`, no `Buffer`, no timers, no `Intl`.
- A figure the host does not report is left out of the line, never shown as zero. Keep that rule in the domain, not in an adapter.
- A new tool is a new folder under `src/infrastructure/` that answers the ports. Do not change the core to fit one tool.

## Data sources and their limits

- Context window: `$.session.usage().context`: `tokens` (absent until the first response of the window) and `window`.
- 5-hour and weekly windows: `.rateLimits[]` with `kind` `five_hour` and `seven_day`, `percentUsed`, and `resetsAt`. The list is empty off a subscription, so the 🕔 and 📅 icons are hidden there. Other kinds (`seven_day_opus`, a gateway's `spend_limit`) are ignored.
- Updates: `session.measure` pushes the figures after each turn. A 60-second `$.clock.every` judges the line again, so a window whose `resetsAt` has passed reads 0%.
- Reset offers (🎁): as of Claude Code 2.1.309, a mod is told of none. The engine fetches them from claude.ai with the account's OAuth credentials and shows them only in its own `/limit-reset` notice. Do not work around that by reading credentials, calling private endpoints, running `/limit-reset` (it spends the reset), or scraping `~/.claude.json`. Wire the offer in `session-usage.ts` only once the mod API reports it.

## Claude Code mod constraints

The mod's static analysis (`claude plugin validate`) rejects code that breaks these rules:

- Write every engine call in full: `$.noun.method(...)`. Pass `$` only to functions declared at the top level of `register.ts`. Never store `$` or a namespace of it in a variable.
- Event names passed to `on` are string literals.
- `hooks/register.js` is generated by `npm run build`. Never edit it by hand. It is committed, because a marketplace install uses it as is. Rebuild after every change under `src/`. CI fails when it is stale.

The API's type declarations are generated per Claude Code build and are not committed. Run `npm run types:sync` to copy them into `types/claude-code/` before type-checking. It finds them in `.claude-plugin/types/` after you load the mod once with `claude --plugin-dir .`, or at the path in `$CLAUDE_CODE_TYPES` (a `claude-code.d.ts` written by the plugin-authoring skill).

## SonarQube quality gate

Project `marcelomiyake_usage-hud` in the SonarQube Cloud organization `marcelomiyake`: <https://sonarcloud.io/project/overview?id=marcelomiyake_usage-hud>. CI (`.github/workflows/ci.yml`) analyzes every push to `main` and every pull request.

Work is done only when both checks pass:

1. The project's gate, the built-in **Sonar way**, on new code. The scan waits for it (`sonar.qualitygate.wait=true`).
2. `scripts/check-sonar-gate.mjs`, which holds **all code** (not only new code) to:
   - Zero open issues of any type or severity: bugs, vulnerabilities, code smells.
   - Every security hotspot reviewed.
   - Coverage of 80% or more (on a pull request, on its new code). The suite covers 100% of lines.
   - Duplication of 3% or less.

The second check exists because the organization's free plan cannot assign a custom gate to a project. A gate with the same conditions on overall and new code, `usage-hud Zero Issues`, is ready in the organization for when it can.

How to keep it there:

- Fix the cause of an issue. Do not add `// NOSONAR`, rule exclusions, or coverage exclusions to make a number pass. If a rule is a real false positive, mark it in SonarQube Cloud with a written reason, and say so in the pull request.
- Only `src/**/*.d.ts` and `scripts/**` are excluded from coverage. Do not widen that list.
- Write a test with every behaviour change, and run `npm run test:coverage` before pushing.
- Before pushing, check for the issues SonarQube most often raises: an `async` function with no `await` (S7503), unsanitized external data in a log line (S5145), nesting deeper than four functions (S2004), the same string literal three or more times (S1192), cognitive complexity over 15 (S3776), and nested ternaries (S3358).

## Commit messages: Conventional Commits

Every commit follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```
<type>(<optional scope>): <description>

<optional body>

<optional footer(s)>
```

- **type**: one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- **scope**: the area changed: `core`, `domain`, `application`, `claude-code`, `build`, `ci`, `deps`, `docs`, `security`.
- **description**: imperative mood, lowercase, no trailing period, about 72 characters at most.
- **body**: what changed and why, wrapped at 72 characters, separated from the subject by a blank line.
- **breaking changes**: `!` before the colon and a `BREAKING CHANGE: <what to change>` footer.
- **footers**: `Refs: #12`, `Co-Authored-By: ...`, in `token: value` form.

Keep one logical change per commit and one small pull request per step. A commit that changes `src/` also includes the rebuilt `hooks/register.js`. `main` requires a pull request, and every review conversation must be resolved before it merges.
